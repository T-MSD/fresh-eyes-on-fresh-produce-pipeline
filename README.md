# Fresh Eyes on Fresh Produce — pipeline + API

Sensei challenge, JunctionX Lisbon 2026. For every camera image and every planogram area, predict
`planogram_compliant`, `stock_level` and `stock_value`.

## Setup

```bash
brew install uv
uv sync                 # core: pipeline + API
uv sync --extra ml      # adds torch, transformers, open_clip, google-cloud-vision
```

Run every script as a module through uv, from the repo root: `uv run --env-file .env python -m src.<script>`.

## Database

Postgres runs in Docker. Credentials come from `.env` (copy `.env.example`).

```bash
docker compose up -d db        # start, data persists in the pgdata volume
docker compose ps              # wait for "healthy"
docker compose exec db psql -U fresh_eyes -d fresh_eyes
docker compose down            # stop; add -v to wipe the data
```

The schema lives in `config/db/schema.py` (SQLAlchemy models, one class per table). Alembic
migrations live in `config/db/migrations/`.

```bash
uv run --env-file .env alembic upgrade head                            # create or update the tables
uv run --env-file .env alembic revision --autogenerate -m "add x"      # after editing schema.py
uv run --env-file .env alembic check                                   # models and DB in sync?
uv run --env-file .env alembic downgrade -1                            # undo the last migration
```

Review every autogenerated migration before applying it.

`uv run --env-file .env pytest` builds a fresh `TEST_DATABASE_URL` database from the migrations
and checks every constraint against it. The name must end in `_test`; pytest drops and recreates
it on each run. Without `TEST_DATABASE_URL` the database tests are skipped.

```
datasets ──< cameras ──< areas >── products >── datasets
   │            │          ▲          ▲ detected_product_id
   │            └──< frames│          │
   │                   │   │          │
   └──< runs ──< predictions ─────────┘     PK (run_id, frame_id, area_id)
                     │
                     └──< tasks             opened and closed frame (NULL while open)
```

Every load of a dataset adds a row to `datasets` (planogram path, images folder, load time) with
its own cameras, products, areas and frames. Nothing is replaced, so earlier runs keep their
predictions. The active dataset is the most recent load.

Every primary key is an integer generated by the database. Cameras, products and areas keep the
planogram id (`6215`, `11908`, `6215_2`) in `external_id`, unique within one dataset: a judge
planogram can reuse the same ids in a later load. Generated ids stay inside the database;
everything outside it uses `external_id`.

Composite foreign keys keep each row inside one dataset: an area's camera and product, and a
prediction's run, camera and detected product, all belong to the same dataset.

A task is one problem on one area in one run: `restock` (empty), `move_product` (wrong product)
or `top_up` (half). It opens on the frame where the problem appears and closes on the first later
frame where it is gone; its kind never changes. `done_at` is the time staff marked it done. Both
frames reference the run's prediction for the area, so deleting a run deletes its tasks.
`(run_id, area_id, kind, opened_frame_id)` is unique, and an area has at most one open task per
run.

## Loading a dataset

`load` adds a planogram and its images folder (`<camera>/<unix_ts>.jpg`) as a new dataset. Each
path comes from its argument, else from `PLANOGRAM_PATH` / `IMAGES_DIR` in `.env`.

```bash
uv run --env-file .env python cli.py load                                  # paths from .env
uv run --env-file .env python cli.py load path/to/planogram.json path/to/images
uv run --env-file .env python cli.py load --dry-run                        # check only
```

Both inputs are parsed and checked before the database is touched; any problem stops the load.
The insert runs in one transaction, so a failed load leaves no partial dataset. Earlier loads,
their runs and their predictions are never touched. A camera folder missing from the planogram
stops the load; files that are not timestamped JPEGs are listed and skipped.

An image is unreadable when its JPEG header is missing or broken, declares a size of zero or
above `MAX_FRAME_PIXELS` (checked before decoding, so a bad header cannot allocate gigabytes), or
does not decode to the size it declares. EXIF rotation may swap width and height; the stored size
is the decoded one, the image the planogram corners refer to. Unreadable images are listed and
stored without a size, so their areas still get a fallback.

## Storing a run

A run is one set of predictions on one dataset load. `run_test --db` stores its output as a run
(`method` `run_test`, params and git SHA recorded) next to writing `out/test/predictions.json`;
`cli.py save-run` stores any submission-shaped file.

```bash
uv run --env-file .env python cli.py load <planogram> <images_dir>      # first: the dataset
uv run --env-file .env python -m src.run_test --data-dir <folder> --db  # newest load, or --dataset-id N
uv run --env-file .env python cli.py save-run out/final_predictions.json --method hybrid
```

The run is stored in one transaction and only if it covers every area of every frame of the
dataset; a missing area, or a frame or area the dataset does not have, stops it with the list and
stores nothing (the JSON file is still written). Areas on unreadable frames are stored with
`is_fallback` set. Confidences stay `NULL`: these methods give no estimate. Score columns stay
`NULL` until there are dev labels to score against.

## Stock strategies (10 Oct 2026)

Two strategies ship side by side. Compliance is the same in both: the zero-shot CLIP flag.

| | Strategy A: blend | Strategy B: purchase rule |
| --- | --- | --- |
| Stock level | 75% fine-tuned network + 25% CLIP classifier, level with the best expected points | "empty" means one typical purchase leaves the tray bare; loose items counted, packages judged by fill |
| Needs | `out/finetune/model.pt`, `out/labels.json` | product groups, OWL-ViT counts, fill percentages |
| Output | `out/final_predictions.before_hybrid.json` | `out/purchase_rule_predictions.json` (regenerated, not tracked) |

**`out/final_predictions.json` is the hybrid:** strategy A plus only the strategy B changes that were
judged right by hand (28 of 1,962 areas). It is the submitted file.

### Strategy A, step by step

Everything runs from `src/`, in this order:

| Step | Command | Output |
| --- | --- | --- |
| crop every planogram area | `uv run --env-file .env python -m src.crop_areas` | `out/crops/` |
| Google Vision labels (hint only) | `uv run --env-file .env python -m src.label_images` | `out/vision_labels.json` |
| CLIP zero-shot predictions | `uv run --env-file .env python -m src.clip_predict --topk 5` | `out/clip_zeroshot.json`, `clip_embeddings.npz` |
| hand-label in the browser | `uv run --env-file .env python -m src.review_tool serve` | `out/labels.json` |
| classifier on CLIP embeddings | `uv run --env-file .env python -m src.train_classifier` | `out/predictions.json` |
| fine-tuned network (all labels) | `uv run --env-file .env python -m src.finetune --final` | `out/finetune/` (`model.pt` and `bundle.joblib` are not tracked) |

`finetune.py` without `--final` holds out 3 cameras and scores the hand labels only. Latest run:
+0.49 stock points per area, 85% exact level, 15 of 19 halves found, identification +0.96 (3 cameras,
79 labels, so rough). All labels are 404 by hand (62 empty, 105 half, 237 full) on the old rubric
(empty <25%, half 25-75%, full >75%); the other 1,558 areas are CLIP's guess and are never used
for scoring.

### Strategy B, step by step

| Step | Command | Output |
| --- | --- | --- |
| group every product by purchase size and method (count or fill) | `uv run --env-file .env python -m src.product_groups` | `out/product_groups.json` |
| count loose items with OWL-ViT v2 | `uv run --env-file .env python -m src.owl_count` | `out/owl_counts.json` |
| label fill percentages in the browser | `uv run --env-file .env python -m src.fill_label_page` | `out/check/fill_labelling.html` -> `out/fill_labels.json` |
| compare cutoff rules on held-out cameras | `uv run --env-file .env python -m src.fill_probe` | printed table |
| build strategy B predictions | `uv run --env-file .env python -m src.purchase_rule_predictions` | `out/purchase_rule_predictions.json` |
| judge where A and B disagree | `uv run --env-file .env python -m src.compare_strategies`, then `--score` | `out/check/compare_strategies.html` |
| keep only the changes judged right | `uv run --env-file .env python -m src.hybrid_predictions` | `out/final_predictions.hybrid.json` |

What strategy B does:
- `product_groups.py` puts each product in a group with a typical purchase and an "empty means N units
  or fewer" number. Products whose names end in KG are not always loose: three 1 KG apples, `CEBOLA NOVA CNT KG`
  and all grapes are packaged on the shelf, so a small override list exists.
- **Count products:** the OWL count turns a tray empty only if strategy A does not already say full.
  Without that guard, 181 full trays became empty.
- **Fill products** (packages, bunches, tomatoes and four overrides): ridge regression on the CLIP
  embedding, trained on 146 hand-labelled fill percentages in 10% steps. Cutoffs: empty 0-15%,
  half 16-64%, full 65-100%.

### Results and limits

On 100 crops where A and B disagreed, judged by hand under the purchase rule (3 judged "neither"):

| File | Right on 97 crops | Points per crop (project scoring) |
| --- | --- | --- |
| A, the blend | 59 | -0.29 |
| B, purchase rule | 38 | -1.08 |
| hybrid (submitted) | 77 | +0.22 |

- B alone lost to A. It only won on fill half-to-full (18 of 22), fill empty-to-full (1 of 1) and
  count empty-to-half (4 of 5); the hybrid takes exactly those 28 changes. I picked those categories
  after seeing the judgements, so the +0.22 is not a held-out estimate.
- The hybrid has no score on dev labels: the 404 labels use the old rubric and train strategy A.
- Cutoffs 0-34/35-79/80-100 and per-group "N units" exceptions did not beat 0-15/16-64/65-100 on
  held-out cameras; the differences were inside the noise (about ±0.4 points).
- Counting failed on packages (YOLO-World found nothing; OWL-ViT was judged unusable by hand on the
  crops checked) and on dense loose trays such as tomatoes, so those products use fill percentages. OWL-ViT agreed with a hand count exactly on 54%
  of 24 crops, within one item on 75%.
- Run and tested under Python 3.14 locally; the repo pins 3.12.

### Run on new images

```bash
uv sync --extra ml
uv run --env-file .env python -m src.run_test --data-dir <folder with planogram.json and the camera folders>
```

It crops the new frames, runs CLIP, the saved network and the classifier, blends them, applies the
one fill rule that survived (a blend "empty/half" becomes "full" when the fill model says >= 65%) and
writes `out/test/predictions.json`. No training, about 20 seconds for 1,962 areas. A frame OpenCV
cannot read has no crops, so its areas get a fallback instead of being dropped: compliant, and the
stock level with the best expected points under the hand-label mix.

It reads only three files, so those are all you need to share:

```
uv run --env-file .env python -m src.finetune --final   # writes out/finetune/
  model.pt          network weights
  bundle.joblib     class order of the network head, CLIP standardisation, classifier, fill model
out/product_groups.json
```

`model.pt` is only valid with the bundle written next to it. `python -m src.finetune --bundle-only`
rebuilds the bundle from `out/crops/index.json`, `out/labels.json` and `out/fill_labels.json` without
training, which is only correct while those still match the run that produced `model.pt`.

`uv run --env-file .env python -m src.run_test --selftest` rebuilds the submission from its own
crops; it differs from `out/final_predictions.json` on 5 areas, the OWL count changes that
`run_test` leaves out on purpose. A product class the network has not seen is scored by the
classifier alone and logged as a warning.

Tracked files under `out/`: `labels.json`, `fill_labels.json`, `product_groups.json`,
`final_predictions.json`, `final_predictions.before_hybrid.json`. Everything else is regenerated.

Review tool keys: 1/2/3 empty/half/full (saves, next), 4/5/6 the same with wrong product,
X wrong product and U unsure (press before 1/2/3), Enter accept suggestion, T todo/all.
