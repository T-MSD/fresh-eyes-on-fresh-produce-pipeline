# Fresh Eyes on Fresh Produce — pipeline + API

Sensei challenge, JunctionX Lisbon 2026. For every camera image and every planogram area, predict
`planogram_compliant`, `stock_level` and `stock_value`.

## Setup

```bash
brew install uv
uv sync                 # core: pipeline + API
uv sync --extra ml      # adds torch, transformers, open_clip, google-cloud-vision
```

Run every script as a module through uv, from the repo root: `uv run --env-file .env python -m src.<script>`.

## Run everything

From a fresh clone to a run in the database and the API serving it. The hand-made inputs
`out/labels.json`, `out/fill_labels.json` and `out/product_groups.json` and the submission
candidates `out/final_predictions.json` and `out/final_predictions.before_hybrid.json` are
tracked; everything else under `out/` is rebuilt by these steps.

```bash
cp .env.example .env                       # then set the Postgres credentials
uv sync --extra ml

docker compose up -d db                    # Postgres; wait for "healthy" in `docker compose ps`
uv run --env-file .env alembic upgrade head

uv run --env-file .env python cli.py load  # dataset/planogram.json + dataset/training from .env

uv run --env-file .env python -m src.crop_areas --data-dir dataset/training     # out/crops/
uv run --extra ml --env-file .env python -m src.clip_predict                     # CLIP embeddings and probabilities
uv run --extra ml --env-file .env python -m src.finetune --final                 # out/finetune/model.pt, bundle.joblib

uv run --extra ml --env-file .env python -m src.run_test --data-dir dataset/training --db   # stores the run and its tasks

uv run --env-file .env uvicorn src.main:app --host 127.0.0.1 --port 8000        # API at http://127.0.0.1:8000/docs
```

`finetune --final` trains the network and is the slow step; `run_test` reuses its output, so
predicting on new frames only needs `cli.py load` and `run_test --db`. Add `--reload` to the
`uvicorn` command while editing the API code: it restarts the server whenever a `.py` file
changes.

Other ways to store a run, and to add tasks to a run stored before runs got them:

```bash
uv run --env-file .env python cli.py save-run out/final_predictions.json --method hybrid --fallbacks out/crops/fallbacks.json
uv run --env-file .env python cli.py derive-tasks <run_id>
```

## Database

Postgres runs in Docker. Credentials come from `.env` (copy `.env.example`).

```bash
docker compose up -d db        # start, data persists in the pgdata volume
docker compose ps              # wait for "healthy"
docker compose exec db psql -U fresh_eyes -d fresh_eyes
docker compose down            # stop; add -v to wipe the data
```

The schema lives in `config/db/schema.py` (SQLAlchemy models, one class per table). Alembic
migrations live in `config/db/migrations/`.

```bash
uv run --env-file .env alembic upgrade head                            # create or update the tables
uv run --env-file .env alembic revision --autogenerate -m "add x"      # after editing schema.py
uv run --env-file .env alembic check                                   # models and DB in sync?
uv run --env-file .env alembic downgrade -1                            # undo the last migration
```

Review every autogenerated migration before applying it.

`uv run --env-file .env pytest` builds a fresh `TEST_DATABASE_URL` database from the migrations
and checks every constraint against it. The name must end in `_test`; pytest drops and recreates
it on each run. Without `TEST_DATABASE_URL` the database tests are skipped.

```
datasets ──< cameras ──< areas >── products >── datasets
   │            │          ▲          ▲ detected_product_id
   │            └──< frames│          │
   │                   │   │          │
   └──< runs ──< predictions ─────────┘     unique (run_id, frame_id, area_id)
                     │
                     └──< tasks             opened and closed frame (NULL while open)
```

Every load of a dataset adds a row to `datasets` (planogram path, images folder, load time) with
its own cameras, products, areas and frames. Nothing is replaced, so earlier runs keep their
predictions. The active dataset is the most recent load.

Every table has an integer `id` primary key generated by the database. Cameras, products and
areas keep the planogram id (`6215`, `11908`, `6215_2`) in `external_id`, unique within one
dataset: a judge planogram can reuse the same ids in a later load. Generated ids stay inside the database;
everything outside it uses `external_id`.

Every timestamp is a `timestamptz` column of type `UTCDateTime`, so every query reads it back in
UTC, whatever the session time zone.

Composite foreign keys keep each row inside one dataset: an area's camera and product, and a
prediction's run, camera and detected product, all belong to the same dataset.

A task is one problem on one area in one run: `restock` (empty), `move_product` (wrong product)
or `top_up` (half). It opens on the frame where the problem appears and closes on the first later
frame where it is gone; its kind never changes. `done_at` is the time staff marked it done. Both
frames reference the run's prediction for the area, so deleting a run deletes its tasks.
`(run_id, area_id, kind, opened_frame_id)` is unique, and an area has at most one open task per
run.

## Loading a dataset

`load` adds a planogram and its images folder (`<camera>/<unix_ts>.jpg`) as a new dataset. Each
path comes from its argument, else from `PLANOGRAM_PATH` / `IMAGES_DIR` in `.env`.

```bash
uv run --env-file .env python cli.py load                                  # paths from .env
uv run --env-file .env python cli.py load path/to/planogram.json path/to/images
uv run --env-file .env python cli.py load --dry-run                        # check only
```

Both inputs are parsed and checked before the database is touched; any problem stops the load.
The insert runs in one transaction, so a failed load leaves no partial dataset. Earlier loads,
their runs and their predictions are never touched. A camera folder missing from the planogram
stops the load; files that are not timestamped JPEGs are listed and skipped.

An image is unreadable when its JPEG header is missing or broken, declares a size of zero or
above `MAX_FRAME_PIXELS` (checked before decoding, so a bad header cannot allocate gigabytes), or
does not decode to the size it declares. EXIF rotation may swap width and height; the stored size
is the decoded one, the image the planogram corners refer to. Unreadable images are listed and
stored without a size, so their areas still get a fallback.

## Storing a run

A run is one set of predictions on one dataset load. `run_test --db` stores its output as a run
(`method` `run_test`, params and git SHA recorded) next to writing `out/test/predictions.json`;
`cli.py save-run` stores any submission-shaped file.

```bash
uv run --env-file .env python cli.py load <planogram> <images_dir>      # first: the dataset
uv run --extra ml --env-file .env python -m src.run_test --data-dir <folder> --db  # newest load, or --dataset-id N
uv run --env-file .env python cli.py save-run out/final_predictions.json --method hybrid --fallbacks out/crops/fallbacks.json
uv run --env-file .env python cli.py save-run out/test/predictions.json --fallbacks out/test/crops/fallbacks.json
```

The run is stored in one transaction and only if it covers every area of every frame of the
dataset; a missing area, or a frame or area the dataset does not have, stops it with the list and
stores nothing (the JSON file is still written). Areas listed in `fallbacks.json` (unreadable
frames) are stored with `is_fallback` set: `run_test --db` does this itself, `save-run` needs
`--fallbacks <file>`. Confidences stay `NULL`: these methods give no estimate. Score columns stay
`NULL` until there are dev labels to score against.

The same transaction stores the run's tasks. Each area's frames are walked in time order,
skipping fallback predictions; an area's problem is `empty` (`restock`), else not compliant
(`move_product`), else `half` (`top_up`). A frame whose problem differs from both the previous
frame (after this rule) and the next frame, when those two agree, takes their problem: one
misread frame neither opens nor closes a task. A task opens on the frame where its problem
appears and closes on the first later frame with a different problem or none, where that
different problem opens its own task. `cli.py derive-tasks <run_id>` stores the tasks of a run
saved before this; it refuses a run that already has tasks.

## API

```bash
uv run --env-file .env uvicorn src.main:app --reload
```

`GET /hour-range` returns the earliest and latest frame timestamps with predictions in the
most recent completed run. All API record queries must use `config.db.queries.latest_run()`
to scope records to the newest completed run by `started_at`, breaking ties by the highest `id`.
Only completed (`done`) runs are selected; an empty newest completed run never falls back to
an older run. Newer `running` or `failed` runs are skipped.

```json
{
  "start": "2025-06-27T08:00:00Z",
  "end": "2025-06-27T20:00:00Z"
}
```

The bounds are full frame timestamps normalized to UTC (`Z`), regardless of the database session
timezone. For a run without predictions,
`start` and `end` are `null`. With no completed runs, the endpoint returns `404` with
`{"detail": "No completed runs available"}`. Interactive API documentation is at `/docs`.

`GET /tasks` returns the tasks of the most recent completed run that staff have not marked done.
It uses the same `latest_run()` selection as `/hour-range`; a newest completed run without
pending tasks never falls back to an older run.

```json
{
  "tasks": [{
    "camera": "6215", "area_id": "6215_2", "product_id": "11908",
    "product_name": "BANANA CAT I CNT KG", "kind": "top_up",
    "opened": { "filename": "1751052241.jpg", "ts": "2025-06-27T19:24:01Z" },
    "closed": { "filename": "1751055841.jpg", "ts": "2025-06-27T20:24:01Z" }
  }]
}
```

Tasks are sorted by priority (`restock`, `move_product`, `top_up`), then by opening time,
camera and area, with creation order breaking any remaining tie. No database id is returned.
Closed tasks are included with their closing frame, so the time slider can tell which were
still open at any moment; `closed` is `null` while a task is open. With no completed runs,
the endpoint returns `404` with `{"detail": "No completed runs available"}`. Interactive API
documentation is at `/docs`.

`POST /tasks/done` marks one task of the most recent completed run as done. The body names the
task with the `area_id`, `kind` and `opened.filename` that `GET /tasks` returns:

```json
{ "area_id": "6215_2", "kind": "top_up", "opened_filename": "1751052241.jpg" }
```

It sets the task's `done_at` and returns `204` with no body; the task then disappears from
`GET /tasks`. Marking a task already done also returns `204` and keeps its first `done_at`.
With no completed runs, it returns `404` with `{"detail": "No completed runs available"}`; a
task not in that run returns `404` with `{"detail": "Task not found in the latest completed run"}`.
An invalid body or unknown `kind` returns `422`.

`GET /predictions?at=&camera=` feeds the Store page: the state of every camera at one moment of
the most recent completed run, with the same `latest_run()` selection as `/hour-range`. Each
camera shows the same frame as `GET /cameras/{camera}/frame?at=`: both use `latest_frames()`,
the newest frame at or before `at` (an ISO 8601 time with a time zone; without `at`, the newest
frame) in the run's dataset, with or without predictions, ties resolved to the highest filename.
A camera without a frame by `at` is left out. The optional `camera` keeps only that camera; a
known camera without a frame by `at` returns `{"cameras": []}`, and a camera that is not in the
run's dataset returns `404` with `{"detail": "Camera not found in the latest completed run"}`.

```json
{
  "cameras": [{
    "camera": "6215",
    "frame": { "filename": "1751052241.jpg", "ts": "2025-06-27T19:24:01Z" },
    "areas": [{
      "area_id": "6215_2", "product_id": "11908", "product_name": "BANANA CAT I CNT KG",
      "status": "wrong_product",
      "prediction": {
        "planogram_compliant": false, "stock_level": "half", "stock_value": 0.5,
        "detected_product_id": "11909", "detected_product_name": "BANANA CAT I CNT KG",
        "compliance_confidence": 0.71, "stock_confidence": null
      }
    }, {
      "area_id": "6215_3", "product_id": "11908", "product_name": "BANANA CAT I CNT KG",
      "status": "unknown", "prediction": null
    }]
  }]
}
```

Every area of the camera is listed, sorted by area number, so `areas` is the camera's full
planogram. An area without a prediction in that frame and run has `status: unknown` and
`prediction: null`; older frames and runs never fill the gap, so an empty completed run shows
every area as `unknown`. Otherwise `status` is `empty`, else `wrong_product` when it is not
compliant, else `half`, else `ok`. Cameras are sorted most urgent first: more `empty` areas,
then more `wrong_product`, then more `half`, then more `unknown`, then camera id, so a camera
without data never looks healthier than one that is fully `ok`. A confidence is `null` when the method gives no estimate. With no completed runs, the
endpoint returns `404` with `{"detail": "No completed runs available"}`.

## Model

### Pipeline

```
crop_areas ─► clip_predict ─► review_tool ─► split_labels ─► finetune ─► run_test
cut areas     embeddings +    hand labels    frozen 80/20    train,        predict
out of        zero-shot       out/labels.json labels/        evaluate,     new frames
frames        compliance                      split.json     final model
```

`src/` holds only this pipeline and the modules it imports. Scripts from finished or rejected
experiments (strategy B, the hybrid, Google Vision hints, relabel queues, the old scorer) live in
`experiments/` and run as `python -m experiments.<script>`; nothing in `src/` depends on them.

### Training procedure

1. **Split once.** `python -m src.split_labels` writes `labels/split.json`: per camera, the latest
   20% of labelled frames are test frames. The split is frozen; it is only rewritten with
   `--force`, so every score is measured on the same frames.
2. **Evaluate on the 80/20 split.** `python -m src.finetune` trains on
   the training frames only (their hand labels, CLIP pseudo-labels and fill labels) and scores
   every method on the test frames. It writes `out/finetune/metrics.json`.
3. **Train the shipped model on everything.** `python -m src.finetune --final` retrains with the
   same settings on all labels, ignoring the split, and writes `model.pt`, `bundle.joblib`, `classes.json` and
   `metadata.json` to `out/finetune/`. The test score from step 2 is the reported score.
4. **Predict.** `python -m src.run_test --data-dir <dataset-folder>`.

This is the only evaluation. Test frames are scored, never trained or tuned on, and no frame
from a camera's first test frame onwards is trained on, labelled or not. Adding labels does not move a frame into the
test set; regenerate the split with `--force` only when starting a new evaluation baseline.

`metadata.json` (with the model) and `metrics.json` (with the evaluation) record what produced
them: time, git commit (suffixed `-dirty` when the working tree had uncommitted changes), every parameter, and the sha256 of `out/labels.json`,
`out/fill_labels.json` and the split file. Training is seeded (`--seed`, default 0), but the
network is not deterministic on the Apple GPU (MPS): runs with the same seed, split and code give
different network scores. The CLIP and classifier scores are exactly reproducible.

`estimate_score --split labels/split.json` scores a predictions file on the test frames only. The
shipped model has trained on those frames, so on its predictions this is not a held-out score.

### Model card

| | |
| --- | --- |
| Task | Per planogram area: compliance (right product or not) and stock level (empty / half / full) |
| Input | Perspective-corrected crop of the area plus the product the planogram expects there |
| Compliance | Zero-shot CLIP: expected product among the top-5 guesses over all store products, or the tray looks empty |
| Stock level | 75% fine-tuned ResNet50 + 25% logistic regression on CLIP embeddings, level with the best expected points; fill rule raises package trays the fill model reads as >= 65% to full |
| Training data | Hand labels (`out/labels.json`), weighted 3x, plus CLIP pseudo-labels with confidence >= 0.6; fill percentages (`out/fill_labels.json`) for the fill model |
| Evaluation | Latest 20% of labelled frames per camera; nothing from a camera's first test frame onwards is trained on |
| Test score (shipped blend, before the fill rule) | +0.74 to +0.88 points per area over three identical runs: stock −0.19 to −0.06, compliance +0.93; 70-73% exact stock level |
| Validation estimate | About +214 to +254 on the 289 validation areas (maximum +578) |

Known limits:
- **Stock is near break-even on unseen frames.** Almost all points come from compliance.
- **Small test set, noisy training.** A few areas change the score noticeably, and reruns of the
  network move the shipped score by up to about 0.2 points per area. The blend weights in `metrics.json`
  swap order between runs, so the 75% network share is not supported over 50% or the classifier
  alone.
- **Off-image areas.** Crop pixels outside the image are painted black, which the models can read as
  an empty shelf (see Crops).
- **Old stock rubric.** The hand labels use empty <25%, half 25-75%, full >75%.
- **The fill rule is not part of the held-out score**: `finetune` scores the blend alone.

### Steps

Install the vision dependencies with `uv sync --extra ml` and run every step from the repository
root as `uv run --extra ml --env-file .env python -m <module>`.

| Step | Module | Output |
| --- | --- | --- |
| crop every planogram area | `src.crop_areas --data-dir <dataset-folder>` | `out/crops/` |
| CLIP embeddings and zero-shot predictions | `src.clip_predict --topk 5` | `out/clip_zeroshot.json`, `clip_embeddings.npz`, `clip_level_probs.npy` |
| hand-label stock and compliance | `src.review_tool serve` | `out/labels.json` |
| group products by fill or count method | `src.product_groups` | `out/product_groups.json` |
| hand-label fill percentages | `src.fill_label_page` | `out/check/fill_labelling.html` -> `out/fill_labels.json` |
| freeze the 80/20 split (once) | `src.split_labels` | `labels/split.json` |
| evaluate | `src.finetune` | `out/finetune/metrics.json` |
| train the shipped model | `src.finetune --final` | `out/finetune/` |
| predict new frames | `src.run_test --data-dir <dataset-folder>` | `out/test/predictions.json` |

Review tool keys: 1/2/3 empty/half/full (saves, next), 4/5/6 the same with wrong product,
X wrong product and U unsure (press before 1/2/3), Enter accept suggestion, T todo/all.

`finetune` builds its training labels from `out/labels.json` and the CLIP outputs. Manual labels
take precedence and weigh 3x; unsure manual labels are excluded from training; unlabelled crops get
the CLIP classifier's level when its confidence is at least 0.6. CLIP guesses are never scored.

### Labels

`out/labels.json` is the source of truth for the hand labels; `src.review_tool` writes it after
every keypress. `labels/dev_labels.json` is the same labels in the organisers' `annotations.json`
format (`src.review_tool export` writes that format to `out/annotations.json`). The two matched
label for label on 19 Oct 2026. `dev_labels.json` is never regenerated: after changing a label in
the review tool, change the same single label in `dev_labels.json`.

`out/fill_labels.json` holds the fill percentages behind the fill rule, keyed like `labels.json`.

### Crops

Unreadable frames are recorded in `out/crops/fallbacks.json`. Submission writers include each
of their planogram areas as compliant and empty; fallbacks have no confidence estimate. The
crop index contains only readable crops. Planogram parsing accepts `productd` as `product_id`
and preserves negative corners. The crop warp does not mask pixels that lie outside the image: it
paints them black, and the models can read that as an empty shelf. This affects the areas whose
polygon leaves the image (`6383_5`, `6383_6`, `6383_7`, `6386_3`, `6386_4` in the training data).
Filling them with the mean colour of the visible pixels made the labelled score worse, so the
black border stays until the models can take a validity mask or be retrained on filled crops.

### Run on new images

```bash
uv run --extra ml --env-file .env python -m src.run_test --data-dir <dataset-folder>
```

It crops the new frames, runs CLIP, the saved network and the classifier, blends them, applies the
fill rule (a blend "empty/half" becomes "full" when the fill model says >= 65%) and writes
`out/test/predictions.json`. No training. If every frame is unreadable, it writes the complete
fallback submission without loading ML artifacts.

It reads only these files, so they are all you need to share (`--selftest` also reads the training
crops it rebuilds the submission from):

```
uv run --extra ml --env-file .env python -m src.finetune --final   # writes out/finetune/
  model.pt          network weights
  bundle.joblib     class order of the network head, CLIP standardisation, classifier, fill model
  classes.json      the class order model.pt was trained with
  metadata.json     what model.pt was trained from
out/product_groups.json
```

`model.pt` is only valid with the bundle written next to it. `python -m src.finetune --bundle-only`
rebuilds the bundle from `out/crops/index.json`, `out/labels.json` and `out/fill_labels.json` without
training. It stops unless the classes of that index are, in order, the ones in `classes.json`, so it
cannot write a bundle that scores the wrong products; a `model.pt` from before `classes.json`
existed needs `--final` again.

A product class the network has not seen is scored by the classifier alone and logged as a
warning; if all products are unseen, network loading and inference are skipped. A product no class
rule knows is scored as generic `fresh produce` by the classifier alone and counted compliant, with
a warning naming it. That generic class takes no part in the class comparison that sets compliance
for the other areas, so it cannot change their flag.

### Submission

The submitted file, `out/final_predictions.json`, is the hybrid from
`experiments.hybrid_predictions`: the `run_test` pipeline plus the OWL-ViT count changes judged by
hand (see `experiments/README.md`). `run_test --selftest` rebuilds it from the training crops and
matches it everywhere except the areas those count changes touched, because `run_test` does not
count items. `out/final_predictions.before_hybrid.json` is the blend before any hybrid change: no
fill rule, no count changes.

Estimate the validation score of a predictions file from the dev labels:

```bash
uv run --env-file .env python -m src.estimate_score [predictions.json] [--labels labels/dev_labels.json] [--validation-areas 289] [--split labels/split.json]
```

It prints the brief's scoring table (a missing area counts as a wrong identification and a stock
level above the real stock), the points per labelled area, and that rate scaled to the validation
set with a 90% interval from resampling labelled frames. The default input is
`out/test/predictions.json`. The shipped model trained on every dev label, so this estimate is
optimistic; the held-out score is the one in `out/finetune/metrics.json`.

Tracked files under `out/`: `labels.json`, `fill_labels.json`, `product_groups.json`,
`final_predictions.json`, `final_predictions.before_hybrid.json`. Everything else is regenerated.

## Camera view

```text
GET /cameras
    → latest completed run's dataset → every camera and its planogram areas
GET /cameras/{camera}/frame?at=<ISO 8601 Z>
    → latest completed run → last frame at or before at → areas and predictions
GET /images/{camera}/{filename}
    → latest completed run's dataset → stored JPEG
GET /areas/{area_id}/stock
    → latest completed run → stock history in timestamp order
```

The camera list lets the frontend show every camera, including one with no frame at the
selected time, without knowing camera ids in advance:

```json
{
  "cameras": [{
    "camera": "6215", "camera_name": null,
    "areas": [{
      "area_id": "6215_1", "number": 1, "product_id": "20923",
      "product_name": "BANANA DA MADEIRA CNT KG",
      "corners": { "top_left": [370, 179], "top_right": [633, 171],
                   "bottom_right": [629, 248], "bottom_left": [384, 255] }
    }]
  }]
}
```

Cameras are sorted by camera id and areas by area number. Cameras without frames or areas are
included; a camera without areas has `areas: []`.

The camera response contains `camera`, `camera_name`, `filename`, `ts`, `width`, `height`
and `areas`. Omit `at` for the camera's latest frame. An aware timestamp is required when
`at` is supplied; invalid or naive values return 422. Frame selection uses the selected
run's dataset, including frames without predictions. Dimensions and camera name may be null.

Every area contains `area_id`, `number`, `product_id`, `product_name`, `corners`
(`top_left`, `top_right`, `bottom_right`, `bottom_left`) and `prediction`, or null when
that frame has no prediction for the area in the selected run. Corners retain negative
coordinates. A prediction contains `planogram_compliant`, `detected_product_id`,
`detected_product_name`, `stock_level`, derived `stock_value`, `compliance_confidence`
and `stock_confidence`. Unknown detected products and confidence estimates remain null.

Stock history is a JSON array of `{ts, stock_level, stock_value, stock_confidence}` for
the area's predictions in the selected run. A known area without predictions returns `[]`.
All ids exposed by these endpoints are external ids scoped to the selected run's dataset.
No completed run, unknown camera or area, or no eligible frame returns 404. There is no
fallback to older runs. The image endpoint also returns 404 for a missing file or a path
escaping the dataset image folder. Interactive API documentation is available at `/docs`.
